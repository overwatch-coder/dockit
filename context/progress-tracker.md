## Architecture Decisions

- **Typography changed from Geist Sans/Geist Mono to Inter/JetBrains Mono.** `context/ui-context.md`'s Typography section originally specified Geist as fixed; the user explicitly requested a different pairing during Unit 1. Inter is used for the UI face (nav, buttons, body, labels), JetBrains Mono for the data face (SKUs, prices, timestamps, tags). `context/ui-context.md` was updated in the same session to keep the doc in sync with this decision, per `context/ai-workflow-rules.md`.
- **shadcn/ui base color deferred to Unit 4.** Initialized with the `neutral` default rather than the indigo-violet (`#5B5FEF`) palette from `context/ui-context.md`, since the build plan assigns color-token/sidebar theming work to Unit 4 ("App shell and static layout"), not Unit 1.
- **Test tooling: Vitest + React Testing Library + jsdom**, chosen by reading Next 16's own bundled docs (`node_modules/next/dist/docs/01-app/02-guides/testing/vitest.md`) rather than assuming carried-over conventions, per `AGENTS.md`'s standing instruction. Tests live in `tests/` (not the docs' default `__tests__/` convention) to match the `/tests/` folder `AGENTS.md` specifies. Vitest's `pool` is set to `"threads"` in `vitest.config.mts` — the default `"forks"` pool hung indefinitely in this environment.
- **`ShopifyToken` is its own model, not fields on `Store`.** `context/00-build-plan.md`'s Unit 2 line lists "OAuth token" as a separate model from "Store" in its Oxford-comma list, and `context/architecture.md`'s Storage Model table gives OAuth tokens their own row. 1:1 with `Store` via a unique `storeId`.
- **Push and sync jobs share a single `Job` table**, not separate `SyncJob`/`PushJob` tables, because `context/00-build-plan.md`'s Unit 6 refers to "the SyncJob/PushJob **table**" (singular). `type: PUSH | SYNC` is the discriminator, per `context/code-standards.md`'s rule to use discriminated unions instead of scattered string comparisons.
- **Product images are not modeled yet.** `context/architecture.md`'s Storage Model table mentions product images, but `context/00-build-plan.md` assigns image handling to Unit 12 ("Draft image upload") specifically. Adding an `Image` table in Unit 2 would be a speculative addition ahead of the unit that actually needs it (`context/ai-workflow-rules.md` rule 7).
- **Prisma 7's new config shape.** This project's Prisma version (7.9.1) uses the new `prisma-client` generator (output to `lib/generated/prisma`, gitignored) and a `prisma.config.ts` file for datasource/migration config instead of the older schema-embedded `url`/`env()` pattern — confirmed by reading the generated files directly rather than assuming Prisma 5/6-era conventions, the same caution `AGENTS.md` asks for with Next.js itself.
- **Account provisioning is lazy, not webhook-driven.** `context/architecture.md` lists exactly three external-caller API routes (Shopify OAuth callback, Shopify webhooks, job scheduler). A Clerk `user.created` webhook route would be a fourth, undocumented external-caller route, so instead the first authenticated request that resolves a session checks for an existing `AccountUser` row by `clerkUserId` and creates `Account` + `AccountUser` together if none exists (`lib/db/accounts.ts`). A concurrent-first-request race is handled by catching the `AccountUser.clerkUserId` unique-constraint violation (`P2002`) and re-fetching once, not by a silent catch.
- **Prisma 7 requires a driver adapter at runtime.** The `prisma-client` generator's `PrismaClient` no longer connects directly from a datasource URL the way older Prisma versions did — it requires an explicit adapter instance (`@prisma/adapter-pg`'s `PrismaPg`, backed by the `pg` package). `lib/db/client.ts` constructs this once as a dev-mode singleton.
- **Neon connection string uses `sslmode=verify-full`, not `require`.** `pg`/`pg-connection-string` emit a deprecation warning treating `require`/`prefer`/`verify-ca` as aliases for `verify-full` and warn that this will change in a future major version; using `verify-full` explicitly in `.env` (both `DATABASE_URL` and `DATABASE_URL_POOLED`) avoids the warning and locks in the current (correct, already-in-effect) certificate-verification behavior.
- **App renamed to Dockit; Clerk CLI used for Unit 3 setup instead of manual key entry**, per explicit user request — `clerk init` handled SDK install, provider wiring, `proxy.ts`, and env config automatically, linked to a pre-existing Clerk application already named "Dockit".
- **Dark mode designed and added**, per explicit user request ("both light and dark configured at once"), even though `context/ui-context.md` originally specified only a light palette. New dark tokens follow the same semantic roles and indigo-violet hue family as light mode, one Tailwind-brightness-step lighter for contrast (e.g. `--primary` `#818CF8` vs light's `#5B5FEF`) rather than inventing an unrelated look. Documented as an explicit new "Dark Mode" section in `context/ui-context.md`. Toggle mechanism is `next-themes` (`attribute="class"`) with a simple sun/moon button in the sidebar footer — not explicitly requested in the build plan's text, but added since defining dark tokens with no way to reach them would be inert.
- **shadcn CSS variable mapping decisions** (gaps `context/ui-context.md` doesn't specify): `--accent` (generic hover) uses a neutral gray, not `--primary-subtle`, since the spec reserves `--primary-subtle` specifically for "selected row background... badges," and tinting every hover state indigo would read as less restrained than the brief wants. `--muted`/`--card`/`--popover` backgrounds reuse `--surface` since the spec doesn't define separate tokens for them. `--sidebar-accent`/`--sidebar-accent-foreground` map to `--primary-subtle`/`--primary` for the active nav item, matching the spec table's explicit "active nav item" usage note on `--primary`.
- **Radius scale uses fixed values, not the multiplier-derived scaffold default.** `context/ui-context.md` specifies exact `6px`/`8px`/`12px`; the original shadcn scaffold derived `--radius-sm`/`-md`/`-lg` as `0.6×`/`0.8×`/`1×` of one base `--radius`, which doesn't land on those exact values. Replaced with direct literals; unspecified larger tiers (`-xl` and up) stay derived from the new `-lg` for continuity.
- **Clerk's trigger components (`SignInButton`/`SignUpButton`) are unstyled by design** — they provide only click/redirect logic, not themed UI, unlike the full `<SignIn>`/`<UserButton>` widgets. They must wrap an actual styled child (our `Button`) to render as anything but bare text; this is not a bug in `@clerk/ui`'s shadcn theme, it's how Clerk's trigger components work.
- **`app/(dashboard)/dashboard/page.tsx` calls `auth.protect()` directly rather than trusting the layout's check via a non-null assertion.** Observed in practice: on a dev-server cold start, a request can reach the page before the layout's `auth.protect()` has fully gated it, and `auth()` (non-protecting) then returns a null `userId`, crashing the `lib/db/accounts.ts` call instead of redirecting. Calling `auth.protect()` again in the page is cheap (idempotent) and removes the fragile assumption entirely.
- **OAuth state is a signed cookie, not a new database table.** The "Connect store" click happens inside an authenticated dashboard session, and the Shopify callback needs to recover which `accountId` initiated it. Rather than add a new `OAuthState` model (a fourth external-caller-adjacent concern not in `architecture.md`'s three-route list, and speculative for a value that only needs to survive one redirect round-trip), the state is `nonce.accountId`, HMAC-signed with `SHOPIFY_API_SECRET`, held in a short-lived `httpOnly` cookie set right before the redirect to Shopify and verified/cleared in the callback.
- **Token encryption lives in `lib/shopify/oauth.ts`, not `lib/db/stores.ts`.** `code-standards.md` says OAuth tokens are "decrypted only inside `lib/shopify/` at the moment of use" — encryption is colocated with decryption for the same reason, so `lib/db/stores.ts` only ever handles an opaque encrypted string and never touches key material.
- **`connectStore` takes `FormData`, not a plain string argument**, so `components/connect-store-dialog.tsx` can pass it directly as a `<form action={connectStore}>` — the idiomatic Next.js App Router pattern for a server action tied to a form, rather than a client-side `onSubmit` handler with manual state.
- **Unit 5's "Connect store" entry point is both the store-switcher dropdown item and a dashboard empty state**, per explicit user request combining both options offered — the dropdown item is always present (so a store can be added even with one already connected, ahead of Unit 21's multi-store switching), and the empty state replaces Unit 3's placeholder specifically when the account has zero stores.
- **`lib/shopify/oauth.ts`'s `normalizeShopDomainInput` accepts a bare store name, a full myshopify.com domain, or a pasted admin URL**, per explicit user request, stripping protocol/path and appending `.myshopify.com` only when the input has no dot at all. It does **not** accept a custom domain as a substitute — Shopify's OAuth authorize endpoint only ever lives on the `*.myshopify.com` domain (a custom domain never serves `/admin`), so a normalized custom domain still fails `verifyShopDomain` in `connectStore` and surfaces a clear validation error rather than silently attempting (and failing) the redirect.
- **`Store.name` is a best-effort field, not a guaranteed one.** `lib/shopify/shop.ts`'s `fetchShopName` runs once, right after token exchange in the OAuth callback; if it fails (network error, unexpected response shape), the store still gets created — `name` just stays `null` and `components/store-switcher.tsx` falls back to `shopifyDomain`. Chosen over blocking the whole connection on a lookup that isn't essential to the OAuth handshake itself.
- **`checkShopExists` is an undocumented heuristic, not a Shopify-guaranteed check.** Confirmed via Shopify's own docs that there's no official "does this shop exist" endpoint. The heuristic (404 on `HEAD /admin` means nonexistent, anything else means it exists) fails open on network errors/timeouts specifically so a transient issue never blocks a valid connect attempt — the real security checks (HMAC, state, shop-format regex) still happen in the callback regardless of what this heuristic says.
- **`connectStore` was refactored from a plain `(formData) => never` action to React's `useActionState` shape** (`(prevState, formData) => ConnectStoreState`), so an invalid/nonexistent shop domain can render an inline error in the dialog instead of redirecting the browser to Shopify's own dead-end 404 page with no way back. This was a direct fix for user-reported behavior, not a preemptive design choice.
- **`disconnectStore` is a plain callable server action, not tied to a `<form>`.** Unlike `connectStore` (a form submission), removal is triggered from a dropdown icon click, so `components/remove-store-dialog.tsx` calls it directly inside `useTransition` rather than binding it to a form's `action` prop — both are valid Next.js server action invocation styles, chosen per how each is triggered from the UI.
- **`Product`/`Variant` got new compound-unique constraints in Unit 7** (`@@unique([storeId, shopifyProductId])`, `@@unique([productId, shopifyVariantId])`), added via a hand-authored migration since `prisma migrate dev`'s interactive confirmation prompt isn't supported in this non-interactive shell (`prisma migrate diff --from-config-datasource --to-schema` generated the SQL, placed manually under `prisma/migrations/`, applied with `prisma migrate deploy`). Needed so `lib/db/products.ts`'s `importProducts` can upsert idempotently — re-running the import (retries, or a future Unit 17 re-sync) updates existing rows instead of duplicating them. Both fields stay nullable for draft (non-imported) products; Postgres allows multiple `NULL`s in a unique index, so this doesn't constrain Unit 9/10's draft-creation path.
- **`importProducts` upserts products and variants as two explicit passes, not one nested Prisma call.** A single `product.upsert({ ..., update: { variants: { upsert: [...] } } })` would need the variant's compound-unique key (`productId_shopifyVariantId`) inside the *update* branch before the product's `id` is known at the type level — Prisma's generated types don't resolve that ambiguity cleanly for a not-yet-existing/being-updated parent. Splitting into "upsert the product, then upsert each variant using the now-known `product.id`" is simpler and avoids fighting the generated types, at the cost of N+1 queries per product (acceptable — `code-standards.md` rule 6, "functions do one thing," favors clarity here, and catalog sizes in v1's scope are small).
- **Shopify's `ARCHIVED` product status collapses into the schema's `DRAFT`,** in `lib/shopify/products.ts`'s `toProductStatus`. `ProductStatus` (Unit 2) is deliberately fixed to `DRAFT | ACTIVE` with no third value — adding one now would be a schema change speculative to this unit's scope, so `ACTIVE` maps 1:1 and everything else (`DRAFT`, `ARCHIVED`) maps to `DRAFT`.
- **The import job fires automatically from the OAuth callback route, not from a UI button.** `context/00-build-plan.md`'s Unit 7 line says "on first connect," so `triggerStoreImport()` is called immediately after `createStoreWithToken` succeeds — kept as a one-line addition to the callback route (business logic itself stays in `lib/jobs/import.ts`, per `code-standards.md`) rather than inlining an `inngest.send()` call directly in the route.
- **Turbopack's dev-server cache can hold a stale generated Prisma client after `prisma generate` runs while the server is up** (surfaced during Unit 7's live verification — a runtime "Unknown argument" error on a compound-unique field that the freshly generated client's own types clearly included). Restarting the dev process (not `rm -rf .next` while it's running — see the existing Unit 5 note on that) picked up the regenerated client immediately. Added as a standing note: after any `prisma generate` while `npm run dev` is already running, restart the dev server before trusting its behavior.
- **`/dashboard` is an overview/analytics page; `/products` is the real product list** — a mid-unit restructure from Unit 8's build-plan line (which literally describes the list living at the dashboard route), per explicit user request. `app/(dashboard)/products/page.tsx` slots into a directory `context/code-standards.md` already reserved for product-related pages, so this isn't a new structural decision, just filling in a route the docs already implied. `components/nav-main.tsx` now has "Overview" and "Products" as separate nav items instead of one "Products" item pointing at `/dashboard`.
- **`imageUrl` added to `Product` mid-Unit-8, not deferred to Unit 12.** Unit 12 ("Draft image upload") is specifically about *draft-state* images going to Vercel Blob before a product is pushed — a different concern from the *published-state* Shopify CDN URL `context/architecture.md`'s Storage Model table already says the app should reference. The thumbnail column `ui-context.md` requires for the product list needed this field to exist regardless, so it was filled in now rather than left as a placeholder-only column.
- **shadcn's default `Badge` (`rounded-4xl`, pill-shaped) and `Card` (`rounded-xl`, a derived/non-exact radius) were edited directly**, not overridden per-call-site. `ui-context.md`'s radius table is explicit and exhaustive ("Minimal and consistent, never pill-shaped... Badges → `--radius-sm`... Cards → `--radius-lg`"), so these are permanent, spec-wide conflicts with shadcn's stock output, not one-off call-site tweaks — the same category of fix as Unit 4's radius-scale correction in `app/globals.css`, which is why editing the vendored component directly (rather than fighting it with `className` overrides everywhere `Badge`/`Card` gets used) is the right call here, unlike the Unit 5 sidebar-icon case where the fix belonged at the call site.
- **`Button`'s `nativeButton` prop must be explicitly set to `false` whenever its `render` prop is a non-`<button>` element (e.g. `<Link>`).** Base UI's `Button` defaults `nativeButton` to `true` and logs a console warning otherwise ("removes native button semantics"). Found live via the dev server's browser console during Unit 8 verification — fixed in the new `components/dashboard-overview.tsx` "View products" button and retroactively in `app/page.tsx`'s pre-existing "Go to dashboard" button, which had the identical unaddressed pattern.
- **Status badge checks `Product.isConflicted` before `status`.** The field has existed on the schema since Unit 2 but nothing read it until now; `ui-context.md`'s product list explicitly names three badge states (Draft/Active/Conflict), so wiring it up now — read-only, no resolution UI (that's Unit 19) — is a direct implementation of an already-specified layout, not new scope.
- **Tiptap chosen for the description rich text editor**, per explicit user request that expanded Unit 10's "core fields only" scope. Headless (no bundled CSS of its own, unlike e.g. react-quill), so its toolbar/output area styles with the project's existing Tailwind tokens instead of introducing a second styling system. Its toolbar deliberately exposes only the marks/nodes the server-side DOMPurify allowlist already permits (bold, italic, underline, H1–H6, lists, links) — StarterKit's blockquote/code/codeBlock/horizontal-rule/strike extensions are disabled rather than left available and silently stripped on save.
- **A brand-new locally-created product's `shopifyProductId` stays `null` until a future push.** Consistent with the project's draft-then-push model (`project-overview.md`) — Postgres treats each `null` as distinct for the `Product`'s `@@unique([storeId, shopifyProductId])` constraint (already noted in Unit 7's decision above), so this required no schema change.
- **Sanitization moved from the product page to the `updateProduct`/`createProduct` server actions.** Unit 9's DOMPurify setup lived in the (then read-only) `/products/[id]` page component. Now that the rich text editor produces client-generated HTML that has to be sanitized before it's trusted — not just Shopify-sourced HTML being displayed — sanitizing at the point of persistence (the server action) is the correct place, not the display page. The allowlist and the forced-safe-link hook are unchanged from Unit 9, only relocated.
- **shadcn's `sonner` toast is the first toast used anywhere in the app**, even though `ui-context.md` has named toasts as a standard component type since that file was written. Nothing before Unit 10 had a save/mutate action worth confirming with one — Unit 8's delete already had inline `AlertDialog` confirmation copy, which covers that case adequately on its own.
